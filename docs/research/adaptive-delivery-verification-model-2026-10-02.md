# Adaptive Goal verification-coordinator model comparison

> Naming: explanatory prose uses Adaptive Goal. Recorded commands, identifiers,
> snapshots, hashes and artifact paths retain their historical names. See the
> [rename note](adaptive-goal-rename-2026-10-05.md).

Status: complete. All ten E controls and ten scheduled F trials are retained.
This is an isolated experiment, not production adoption.

The completed [D/E comparison](adaptive-delivery-main-thread-model-2026-10-01.md)
supports using Sol/medium for the main thread. The next hypothesis is that raising
only verification coordination to Sol/medium will preserve provider boundaries
and complete assessment handoffs while implementation and review coordination
remain on Luna. The selected sample supports better provider separation, but
does not establish better overall reliability. F has five confirmed contract
passes, three contract failures and two interrupted trials. Keep it as an
experimental candidate while discussing the remaining failures.

## Failure and recovery analysis

### Provider boundaries

Four E real-review trials let the verification coordinator absorb review's
coordination work. In F, all five real-review trials delegated initial and
follow-up review to separate Luna/medium capability assignments. Their independent
readers retained Sol/xhigh. Raising verification coordination removed this
specific observed failure pattern in the selected sample.

That does not establish complete contract compliance. A separate provider can
still return an incorrect or incomplete result, and its caller must reconcile
that result without changing the historical record.

### Incorrect metadata and lost history

- **F focused repair 2:** the follow-up added a trailing `d` to the original
  40-character Git blob identity. The original assessment and provider evidence
  retained the correct identity. The wrong value was already in the assessment
  draft; exact rendering preserved that error. This fails historical binding and
  evidence correctness, while the actual repair and current-target evidence pass.
- **F real review 3:** the initial assessment wrongly called an earlier check
  stale even though no content change had occurred. Separate current provider
  checks still supported the verdict, so this is an evidence-accuracy failure
  without failure of the required current-check contract.
- **F real review 5:** the provider first returned a completed blocked result
  because it misread delegation permission. After receiving follow-up, it ran
  independent readers and returned a completed `no_progress` result, bound to the
  earlier result at the same target. A further follow-up restarted from the
  original review, set previous verification to `none`, and returned `clear`.
  Verification accepted the claim that no previous repair verification applied.
  The code repair and independent resolution evidence were correct, but the
  completed prior results were omitted from the final assessment's history.
  This fails capability compliance, evidence correctness, and evidence
  preservation under the frozen contract. The old artifacts remain retained in
  the experiment; their retention does not repair the participant's handoff.

Native messages remain encrypted. The public trace proves the reset and its
acceptance, but cannot establish which participant authored the instruction to
reset history. Do not attribute it exclusively to the Luna provider or the Sol
verifier.

### Presentation

F real review 4 paraphrased the rendered assessment's opening paragraph. The
remaining sections and evidence survived unchanged, and the meaning was
preserved. This fails verification's current exact-stdout contract but passes
semantic evidence preservation. Review's previously relaxed presentation rule
does not change verification's separate rule.

The earlier E focused repair 2 failure was materially different: its shortened
follow-up omitted required scope and history. Keep harmless rewording separate
from missing evidence when discussing any future contract change.

### Recovery and helper paths

F repeatedly looked for verification's renderer at the plugin root instead of
inside the installed skill. Most corrected the path within the same assignment.
In real review 2, the initial verifier returned no final assessment; in real
review 5, it explicitly reported the renderer unavailable. The main thread
continued natively, resumed the same verifier, and obtained its complete result
before delegating repair. The empty first return in real review 2 remains an
attribution gap: the failed path and eventual recovery are observable, but the
reason for the empty native return is not independently established.

Real review 1 also recovered a reader's wrong helper path. Real review 5 corrected
the provider's mistaken refusal to delegate. Its later history reset demonstrates
why a successful retry alone does not establish correct recovery.

The incident ledger records six recovered and five unrecovered issues in E,
versus nine recovered and six unrecovered issues in F. These are descriptive
counts from encountered problems, not matched injected faults or a comparative
recovery rate. F's unrecovered issues comprise the wrong blob identity, stale
check annotation, exact-output deviation, history reset and two capacity stops.

### Host capacity

F focused repair 4 stopped after implementation and the main thread's current
check had passed, while follow-up verification was still incomplete. The native
root completion event explicitly records `server_overloaded` and “Selected model
is at capacity.” The child was then interrupted. This is a confirmed host
failure; the full capability result, final evidence handoff and whole-tree token
total remain unknown. Keep the failed scheduled slot; do not replace it with a
more favorable retry. Long quiet intervals before the fatal event are observed,
but their causes are not independently established.

F focused repair 5 stopped with the same independently retained native error
during initial verification. Its Sol verifier had delegated a separate Luna
provider, but neither returned a result before interruption. No implementation
assignment occurred. The same unknown classifications apply. Two observed host
errors in a historical comparison do not establish a general model-availability
difference.

### Eval artifact selection

The frozen real-review check chooses a report using `sort | tail -n 1` over
randomly named `darrow-review.*` directories. In F real review 5 it chose the
older `xl528il4` blocked report, while the final response cited `5o987fl9`.
The retained records establish this selection defect. The frozen task grade
remains failed; no check or score was changed during the comparison. Correcting
selection would not remove the separately observed history-reset failure.

## Recommendation and next decisions

Keep Sol/medium verification as a promising experimental route for preserving
provider separation. **Do not adopt it as a complete reliability fix yet.** The
sample removes the observed provider-absorption pattern but retains material
history and metadata errors, a strict presentation failure and two unknown
completed outcomes. Historical controls, five slots per case and encrypted
assignments limit causal conclusions.

Discuss these next steps before further implementation:

1. Correct the eval's report selection to follow the returned candidate-bound
   artifact, preserving the old grade and calibrating against stale-report and
   history-loss counterexamples. Keep the older incomplete-assessment ordering
   proposal separate.
2. Decide how to represent a corrected assessment at an unchanged candidate.
   The current machinery can derive `no_progress` when reusing a completed
   blocked result at the same target. Dropping that result to obtain `clear`
   violates today's history contract. Any correction/supersession rule needs
   explicit authority and preserved lineage; a new model alone cannot settle
   that contract question. Keep review and verification unchanged until this
   decision is discussed.
3. Consider a separate change for helper-path resolution and mechanically copied
   identities. Repeated renderer-path mistakes and the blob typo remain concrete
   risks after the model change. Separately decide whether verification should
   allow meaning-preserving presentation changes, as review already does.

If these changes are approved, validate them independently before another bounded
live comparison. Any additional capacity reruns should be reported as new trials,
without replacing these scheduled slots. No production adoption, capability edit,
commit or push is part of this completed experiment.
