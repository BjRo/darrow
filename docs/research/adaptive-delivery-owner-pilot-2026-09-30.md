# Adaptive Delivery owner pilot

## Result and recommendation

All **60 fresh trials** are complete: four cases, three arms, five trials per
case and arm, on Codex `gpt-6-luna/medium`. Keep the native owner as the current
production path. Repair the experimental transport and demonstrate actual native
continuation before considering adoption. The next bounded experiment is proposed
below; it has not been implemented.

| Measure                            | A: unchanged native owner | B: app-server, no goal | C: app-server, native goal |
| ---------------------------------- | ------------------------- | ---------------------- | -------------------------- |
| Common task checks                 | **19/20**                 | **9/20**               | **15/20**                  |
| Original unmodified task grades    | 18/20                     | 4/20                   | 6/20                       |
| Accepted execution owner           | 20/20                     | 14/20                  | 18/20                      |
| Error-free core transport          | 18/20                     | 13/20                  | 16/20                      |
| Latest owner final returned        | 18/20                     | 14/20                  | 16/20                      |
| Any completed owner final observed | 19/20                     | 14/20                  | 17/20                      |
| Configured activation checks       | 5/5                       | 5/5                    | 5/5                        |
| Mean harness duration, seconds     | 275                       | 247                    | 264                        |

The original grades include architecture checks that the app-server arms cannot
satisfy; they remain intact and are not the comparison score. Common task passes
also contain supplemental contract misses identified below. These results do not
establish a fully compliant 5/5 composition case. Duration includes early failed
launches and excludes grading; a lower mean is not a speed or cost advantage.

The composition hypothesis has direct support: obligations disappear at the
owner-to-verification handoff, at verification's fresh-provider boundary, and
during completion relay. The prototype introduces additional launch and cleanup
defects. C performs better than B on common task checks in this sample, but **no
automatic goal continuation was observed**. These trials do not establish a
persistence benefit or justify replacing the native owner.

Every accepted C goal is **185–593 Unicode characters**. The adapter enforces the
4,000-character limit before owner creation. Workflow and assignment use separate
developer/user fields, but repeated task facts in developer instructions leave
the requested priority partition incomplete. A's encrypted-launch attribution
gap and every previous failure remain recorded.

## Authorized experiment

The user approved keeping the native control unchanged despite its encrypted
launch messages. Outcome comparisons include all arms. Launch omissions versus
execution drift remain unknown wherever the retained evidence cannot establish
which instructions reached the owner.
Native feedback message bodies are encrypted as well; same-owner contact and
subsequent behavior remain observable, but exact feedback preservation does not.
The app-server arms expose the execution owner's submitted contract, not the
plaintext of its later native assessment-agent messages. Those nested launches
retain the same encryption limitation.

The user also requested a compact native goal and workflow instructions supplied
as developer instructions. The experiment partitions the compiled assignment:

- **Developer instructions:** the sole-owner role, selected workflow and sequence,
  capability bindings, assurance and repair rules, feedback rules, and required
  completion evidence. These govern the workflow within the authorized task.
- **User assignment:** the requested outcome, acceptance, scope, preserved work,
  permissions, publication limits, originating evidence, and task-specific checks.
  Later user corrections retain their normal priority over this assignment.
- **Goal:** a short outcome and completion condition pointing to those complete
  instructions. Reject objectives exceeding 4,000 Unicode characters before
  starting a server or owner. Never truncate or replace the full instructions.

B and C use the same partition, model/effort policy, installed capabilities and
transport. Only C attaches the goal. A remains byte-for-byte unchanged. Therefore
A versus B measures the combined transport/context change; B versus C measures
enabling the native goal, including its objective reminder and automatic
continuation. An outcome difference alone does not isolate which mechanism helped.

The transport preserves these separate fields, but the parent sometimes repeats
task-specific criteria, scope and authority inside developer instructions. This
is an observed partition defect, not evidence that later user corrections would
override those repeated facts. The pilot's status requests do not test a material
scope or authority correction. A follow-up must remove that duplication before
claiming the intended instruction-priority behavior.

## Experiment invariants

1. Preserve parent preflight, readiness, risk, capability binding and route
   selection. Parents use Codex `gpt-6-luna/medium`; owners use the selected route.
2. Launch one execution owner. An app-server owner is a separate root thread,
   not a native child. Do not fabricate parent/child provenance.
3. Submit complete instructions before execution. Retain submitted instructions,
   the returned thread/route, goal transitions, public tool results, provider
   evidence, the actual final owner response and the parent's relay.
4. Match four available assessment slots: the native parent retains its limit of
   five spawned threads; the app-server owner has four. Enable only reviewed
   fixture hook definitions. Keep review and verification unchanged.
5. Codex owns goal continuation. The transport does not repair, verify, schedule
   providers, retry work, choose routes or create replacement owners.
6. Transport feedback to the same thread without resetting its goal accounting.
   Completion requires a completed turn and its `final_answer`, with terminal
   goal state in C. Do not accept commentary or goal state alone as evidence.
7. Retain original runner grades, including incompatible native-owner/no-goal
   checks. Report common behavior and transport-specific boundaries separately.
8. Preserve source isolation, fixture tools and all prior results. Freeze inputs
   before live delivery trials. Capture evidence before fixture cleanup without
   injecting instructions or changing the runner's returned result.

## Scheduling and scoring

All delivery trials run sequentially. The runner's active-record identity is
shared across the three candidate variants of a case. Initial concurrent launch
attempts for cadence C1 and A3 were rejected before model execution. Those two
setup failures remain recorded; distinct setup retries supply their actual first
model trials. No runner behavior was changed to bypass the lock.

Original task grades remain intact. The common-behavior score excludes the
unchanged native-owner/no-goal transcript checks and reports them separately.
Positive transport evidence establishes the accepted owner, observed effective
route and actual final response. This is separate from completing the task.
The goal transport boundary accepts every supported terminal state, including
blocked or host-limited results; task completion and the legitimacy of that
state require separate evidence. The analysis initially accepted only `complete`;
correcting it to match the frozen client changes no first-47-trial score.
Instruction partition and parent relay require inspection of retained public
contracts and results; a structurally valid JSON request is insufficient.

The B client does not query final goal state: its `goal: null` alone is not proof
that the owner never created a goal. Its no-goal boundary also inspects retained
goal-control calls and app-server notifications. C binds returned objectives and
creation timestamps to the submitted goal and checks that no token budget was
introduced. These are bounded public observations, not proof against arbitrary
unobserved dynamic calls.

Track a returned final separately from error-free transport. In combined-repair
B1, the parent discarded the running shell session metadata and requested
feedback while the launch helper was active. The host rejected the second writer.
The original owner completed, and later status turns returned normally. This is
a parent wait-handling failure with a successful engineering outcome. It is not
an absent eventual final, or evidence that the no-goal arm created a goal.
The analysis keeps the rejected operation while separately reporting the latest
returned final and the goal states on successfully returned results.

Combined-repair C1 passed task and transport checks but failed manual evidence
inspection. The owner returned complete inline QA results and said there were no
separate QA artifact paths. The parent instead labeled two review-only files as
complete verification outputs containing QA. The retained files confirm that
claim was false. Preserve the passing task grade and separately fail the evidence
relay boundary; goal completion did not prevent this parent-side error.

In particular, a passing native control may send an interim result and then
have its owner interrupted when the parent finishes. Keep its passing task
grade and separately report the missing terminal owner response. Do not infer
the encrypted interim message's content.

Raw parent token totals do not cover the separate app-server process. Goal usage
also has its own accounting boundary. Preserve these measurements separately;
do not present either as comparable total execution cost.

## Findings

These observations combine the original scores with retained public evidence:

- **Launch preparation can lose obligations.** Cadence B1 omitted the required
  compact-goal field. Cadence B2 launched an owner but did not unambiguously carry
  forward the expected-failure check. Combined-repair B2 produced invalid JSON by
  decoding escaped newlines inside a JavaScript template string. The first and
  third failures created no owner; persistence cannot act before launch.
  Capability routing B5 also fails JSON parsing, this time from invalid
  backslash-backtick escapes while manually composing the heredoc request.
  Actual-capability B1, C1 and C2 also fail JSON parsing before owner creation; static
  decoding of their retained launch commands reproduces invalid JSON. No check,
  review, verification or repair executes in those trials.
  Combined-repair B3 confused an existing candidate with an accepted owner and
  attempted feedback before any launch. It then ran the task check in the parent
  and stopped on the missing-owner error.
- **Preflight can miss an installed capability.** Capability routing B3 searched
  tool names and project fixture skills, then refused to launch because it said
  verification was unavailable. Passive capture retains the installed
  `verify-change` body and marketplace copy. Its public tool calls never read
  that skill. The exact initial advertisement is not retained, so the narrower
  cause of the discovery miss remains unknown. No owner was created.
- **The parent can finish before an owner final.** Cadence A3 passed task checks
  but the owner was interrupted after the parent completed. Its interim message
  is encrypted, so the exact evidence delivered there remains unknown.
  Capability routing A5 differs: the initial owner turn and a status correction
  both returned completed finals. Two parent follow-up requests led to a further
  trailing turn, which was interrupted when the parent finished. Preserve its
  complete evidence return and the failed latest-turn boundary separately.
- **A valid owner result can be damaged during relay.** Combined-repair C1
  completed its goal and returned correct inline assessment evidence. The parent
  then made false claims about which artifacts contained that evidence.
  Native combined-repair A3 made the same artifact-content error first in the
  owner response; its parent propagated it. Both error locations are observed.
- **Waiting remains a transport obligation.** Combined-repair B1 requested
  feedback while the first helper still held the thread, producing an active
  writer error. The owner eventually completed; preserve both observations.
- **The prototype can destroy goal state while handling overlapping feedback.**
  Actual-capability C3 sends a status request through a second helper while the
  original writer is active. The host correctly rejects the resume. The rejected
  helper's cleanup clears the live goal anyway. The original owner completes the
  repair and closed review; its attempt to mark the goal complete fails because
  the goal is absent. Result collection then crashes on `goal: null`, both after
  the original turn and a later explicit status turn. Passive capture retains
  two complete owner finals, but the parent receives transport errors and
  reports blocked. Repository and provider checks pass; the semantic task check
  fails. This is a prototype defect, not evidence against Codex persistence.
  No actual interrupt request or automatic continuation occurred. Follow-up
  criterion reconciliation and provider evidence are retained, although that
  context also omitted the coordinator's required assessment renderer.
  Actual-capability C5 repeats the cleanup bug after the parent loses its running
  process handle by printing only command output. Four competing feedback calls
  are rejected; the first clears the active goal. The parent ends without
  collecting the original operation. Readers have returned the initial finding,
  but no coordinator or owner final, repair or closed follow-up is retained. This
  trial loses unfinished execution, whereas C3 loses evidence of a completed repair.
  Neither trial has an actual interrupt request in the retained transport log.
- **Status correction can turn success into a false evidence blocker.**
  Combined-repair B4 passed repository and assessment-sequence checks. Its owner
  initially reported completion, then treated the complete inline QA results as
  incomplete summaries when asked for fuller evidence. The parent relayed the
  resulting blocker. Original owner command outputs retain the complete reports;
  this does not establish every detail of the resumed model's internal context.
- **Publication can precede the required coordinator assessment.** Capability
  routing A3 read the verification skill, directly delegated independent review,
  and then committed and published. No coordinator invocation appears in the
  retained owner or reviewer calls, and no separate combined assessment returns.
  The owner acknowledged the missing assessment
  on follow-up, and the parent reported blocked. The execution failure is proven;
  the encrypted native launch prevents separating launch omission from drift.
  Its original parent-work check also rejects `list_agents`. That call exposed a
  nested reviewer's result; it was agent-status inspection, not observed
  repository or external work. Keep that distinction with the original failure.
- **Passing task checks can hide a collapsed verification handoff.** In
  capability routing A2, A4, B1, B4, C1, C3 and C5, independent review returns but
  no complete separate coordinator result returns before publication. The owner
  supplies the combined assessment itself. C1's assessment child is named
  `verification`, but it reads the review skill and returns review only. C3
  explicitly reconciles criteria in owner commentary before committing. The
  B/C submitted contracts preserve the verification-before-publication gate,
  establishing drift during execution. A's encrypted launch leaves that
  attribution unknown. Retain all passing task grades and separately fail this
  handoff boundary; the goal's complete status did not enforce it.
- **Goal state can disagree with acknowledged delivery status.** Capability
  routing C4 publishes and marks the goal complete after the same collapsed
  handoff. On status correction the owner acknowledges the missing combined
  assessment, and the parent reports blocked. The stored goal remains complete.
  Its transport checks pass, but the task fails. A separate report file was not
  required for this inline fixture; missing coordinator evidence is the defect.
- **Reading the coordinator does not establish its complete execution.** In
  actual-capability A2, both assessment contexts read verification and review,
  run the real review and closed follow-up, and return valid provider reports.
  They omit the coordinator's retained-report renderer; the initial response
  states review `fail` without the coordinator's `progress` conclusion. The
  owner supplies combined-clear wording later. The repair and all original
  grades pass, but the complete coordinator handoff is missing. This finding
  concerns the returned contract, not agent names or agent counts.
  Actual-capability A3 completes the initial coordinator handoff correctly, but
  its follow-up coordinator returns the provider report verbatim instead of its
  own complete rendered assessment. The repair still passes. Its original task
  grade also rejects four parent `list_agents` calls; retained parent calls show
  status inspection and waits, with no repository or external work.
- **Constraints and evidence meanings can change during composition.**
  Actual-capability B2 returns a complete rendered coordinator assessment but
  blocks repair. It treats the execution owner's Luna/medium route as a required
  reader route, rejecting the review-selected Sol/xhigh readers. The submitted
  owner contract does not explicitly impose Luna on readers; encrypted nested
  messages leave the first introduction of that constraint unknown. It also
  treats `resolution_evidence` as present-state proof, although review defines
  it as behavior that would demonstrate resolution. The reader's phrase
  "current pinned candidate" contributes ambiguity. The real finding is
  retained; its interpretation prevents repair. This is a task failure with a
  successful transport and coordinator return.
  Actual-capability B3 repeats the route-scope error before either independent
  reader launches. Its complete blocked assessment and owner response return
  successfully, but no repair runs. Persistence is not established as a remedy
  for that incorrectly scoped constraint.
- **Relative references can acquire the wrong owner.** Actual-capability B4
  repairs the candidate after a valid initial assessment, then its follow-up
  context looks for review's `references/fix-verification.md` inside verification.
  Verification's retained public instruction links only to `references/follow-up.md`.
  The context reads the correct documents too, but still refuses on the invented
  prerequisite. The owner and parent relay the false package blocker. This is
  reference-owner confusion during composition, not a missing packaged file.
- **The owner can substitute for the coordinator even when rendering succeeds.**
  Actual-capability C4's assessment contexts return correct provider reports,
  without their complete coordinator assessments. The owner renders the initial
  progress assessment itself, then repairs successfully. The final relay treats
  the closed provider report as the full follow-up assessment. The launch required
  the coordinator handoff, so this is execution drift despite passing task and
  transport checks. The provider file contains the repair evidence actually
  quoted; this differs from the false QA-artifact claims above. Two explicit status
  turns preserve goal identity. One lists the existing report directory; neither
  performs further checks, assessment, repair or mutation.

The initial cadence case scores A **5/5**, B **3/5**, C **5/5** on common task
checks. Error-free core transport scores are **4/5**, **4/5**, **5/5** respectively.
These results do not yet isolate a persistence benefit: B's failures involved
launch preparation, and the A/C completion difference also changes transport.

All 16 C goals with returned terminal state completed during their initial
execution turn. The other two accepted C goals were cleared by the prototype's
rejected-feedback cleanup. Two C trials never created an owner. Later observed
turns were explicit parent status requests; no automatic continuation was observed
anywhere in the pilot.

Correct repairs and complete rendered coordinator output are possible:
actual-capability A1, A4, A5 and B5 demonstrate those stages. A5 also recovers a
reader-launcher path error. B5 preserves its wait handle and needs no competing
writer. However, the final audit found another collapsed boundary in these
otherwise positive examples. The unchanged verification skill's step 3 requires
one fresh bounded **review-provider context**, which then creates its own fresh
axis readers; it explicitly forbids switching to the provider inline.

In A1 and A5 follow-up, A4 and B5 initial/follow-up, and C3 initial/follow-up,
the coordinator executes review preparation, reader launch and result mechanics
itself. Its children return axis JSON, rather than a complete provider response
from a separate context. C5 begins the same inline-provider execution before its
transport failure. The independent readers still use Sol/xhigh and produce valid
evidence; the violated boundary is between coordinator and provider. This is
established from actual commands and returned results, not agent names or a fixed
count. A1, A3 and A5 initial assessments provide counterexamples with the required
separate provider context and rendered coordinator return.

Consequently, all five task-passing A trials in the actual-capability case retain
at least one supplemental composition-contract miss: A1/A4/A5 collapse the provider
boundary, A2 omits the complete coordinator return, and A3 omits that return on
follow-up. Complete rendering alone was too narrow a positive-control claim; the
final assessment preserves this correction without changing any original grade.

## Interpretation limits

- Five trials per case and arm are a bounded sample, not a reliability guarantee.
  These four cases do not replace the full Adaptive Delivery baseline.
- A versus B changes both transport and instruction context. B versus C adds the
  native goal, but any difference may come from its initial reminder rather than
  automatic continuation. Failed launches remain in the denominator.
- All accepted execution owners selected Luna/medium. The actual review readers
  use their capability's higher route. This does not test other execution routes,
  Claude Code or native Windows behavior.
- A's actual launch and feedback text remain encrypted. B/C expose the execution
  contract, but their nested native assessment messages remain encrypted. Public
  actions and outputs establish some defects without locating their first cause.
- The supplemental handoff and artifact inspections expose gaps in passing task
  checks. They are diagnostic findings, not a newly calibrated replacement score.
  Rendering omissions and missing semantic assessments are distinguished above.
- Status-only feedback does not establish how material user corrections interact
  with duplicated developer-level task facts. That partition defect stays open.

## Follow-up candidates for discussion

These are proposals, not changes to the frozen participants or shipped plugins.
Coverage is complete; discuss these choices before changing the architecture.

1. **Remove launch serialization from the model's work.** Accept raw instruction
   files and the already selected route through a narrow bundled entrypoint.
   Let Python serialize the app-server request. Keep the compact goal limit and
   the developer/user partition, with task-specific facts and authority in the
   user assignment. Return one accepted owner identity and preserve the running
   operation's wait handle. This addresses observed pre-launch and wait errors;
   it does not enforce engineering quality.
   Keep one controlling writer. Rejected concurrent feedback must leave the
   existing operation and its goal untouched; cleanup may only affect the
   operation that owns execution. Handle missing goal state explicitly and
   retain any completed owner final alongside the transport error. In-flight
   feedback needs the same controlling connection or an explicit wait boundary.
   Validate before creating a thread. Discuss allowing correction of a proven
   pre-creation input error while continuing to prohibit duplicate or replacement
   owners after an accepted or ambiguous launch; the frozen pilot forbids those
   input retries and preserves their failed outcomes.
2. **Make the verification handoff explicit in Adaptive Delivery.** Supply the
   installed verification skill, acceptance-verification intent, candidate,
   criteria, selected review binding and prior finding history as one bounded
   invocation. Require its complete public assessment to return to the same
   execution owner before repair, publication or completion. Keep inline results
   valid when the provider uses them. Do not infer coordinator execution from a
   child name, a review pass or owner-authored reconciliation. Keep review and
   verification unchanged; any proposed invocation helper must remain transport
   and evidence handling, without a second engineering controller.
   Scope the execution-owner route separately from the provider's reader route;
   the former is not an override of the latter. Preserve the distinction between
   observed finding evidence and the behavior that would demonstrate resolution.
   Preserve both required returns: verification to the engineering owner, and
   the fresh provider to verification. Provider-owned axis readers establish a
   different isolation boundary and cannot substitute for either return.
3. **Treat persistence as a separate claim.** Preserve goal accounting and test
   an actual automatic continuation before attributing improvements to it.
   A goal marked complete is the owner's claim, not independent proof of every
   delivery obligation. Returning its current complete assessment accurately to
   the parent remains a separate requirement.

A follow-up should stage these changes so their effects remain distinguishable:

1. Repair and test the experimental transport only: structured request creation,
   operation-owned cleanup, one writer, missing-goal handling, and preservation
   of completed responses alongside errors. Correct the instruction partition so
   workflow remains in developer instructions and task facts and authority remain
   in the user assignment. Keep the 4,000-character goal limit.
   Before live trials, require deterministic coverage for newline/backtick/Unicode
   request serialization, rejection without goal deletion, absent goal state with
   a completed final, and same-owner feedback without a competing writer.
2. First require a separate bounded diagnostic that demonstrably exercises
   automatic continuation and in-flight feedback. Then repeat B/C on combined
   repair and actual review/verification at n:5 per arm (20 fresh delivery trials).
   Retain this pilot as the baseline; count every failed launch in the new
   comparison as well.
3. After transport is reliable, discuss a separate orchestration change for the
   complete verification handoff. Compare it with the unchanged native control.
   Discover capabilities through the host, preserve their public contracts and
   reference ownership, and scope execution and provider routes separately. Do
   not add a cross-plugin registry or an engineering scheduler to the transport.

This is a proposed next experiment, not authorization to implement it. The
current prototype's transport defect prevents adopting it as the production owner
path, and these trials have not established a persistence benefit.

One larger architectural alternative for discussion is allowing a goal-backed
owner to execute verification in its own bounded turn, return that capability's
complete assessment, and let the host continue the still-active delivery goal.
Independent review would retain its separate readers. This could remove one
handoff, but it changes the current coordinator-return arrangement and must
establish read-only assessment boundaries, preserved repair accounting and real
automatic continuation. It is not implemented or measured by this pilot.
