# Implement approved work

Require explicit user invocation of implement or preserved delegation of the
same bounded work from an explicitly invoked enclosing recipe or orchestration.
An approved ticket/specification, ordinary engineering intent, installation,
or an unauthorized helper merely naming implement supplies no invocation
authority. Without that authority, report the invocation gap before provider
discovery, orchestration, implementation, assessment, commit or publication.

Read [host and authority compatibility](../../references/COMPATIBILITY.md).
This explicit recipe carries approved work into Adaptive Goal. It owns no
controller, queue, lifecycle ledger, repair budget or completion decision.
Installation and ordinary implementation intent never activate it.

## Preserve the caller and approved intent

If this is a bounded implementation assignment from an existing Adaptive Goal
owner, keep that owner and its exact bindings, scope and allowed effects. Follow
only the assigned implementation work below and return evidence to that owner.
Do not invoke Adaptive Goal, create a goal, coordinate independent assessment,
or add commit/publication effects in the worker. An assignment's narrower
permissions take precedence over this recipe's standalone defaults.

Otherwise, accept the user's approved specification or unambiguous ticket.
For a ticket reference, fetch its authoritative content through the configured
tracker's available read operation and state its title before implementation.
Resolve an ambiguous reference or unavailable authoritative input before mutation;
do not switch providers, invent intent or mutate tracker state.

Carry the acceptance criteria, constraints, existing work, agreed test seams,
readiness evidence and allowed effects unchanged. An approved spec is not itself
a readiness assessment. Adaptive Goal selects readiness under its public
contract; preserve an applicable already-ready result for the same scope.

## Bind required public capabilities before mutation

Discover each provider through the active host's advertised skill catalog and
read its exact supplied public instructions, using the host-native skill reader
or invocation facility. On Codex do not invent a Claude Skill tool. A tool-list
search alone cannot establish that an advertised skill is missing.

| Required intent             | Contract to preserve                                                                                            |
| --------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Adaptive Goal orchestration | One native main-thread continuation and acceptance owner; its readiness, placement, repair and completion rules |
| Selected Matt TDD           | Test-first vertical slices at inherited approved public seams                                                   |
| Independent Review          | Fresh independent assessment of the exact candidate; native findings, evidence and closed repair history        |
| Principles-first approach   | Effective routing and applicable guidance within the same scope and authority                                   |

These are required providers for standalone implement, not optional suggestions.
If any is absent or incompatible, report the exact missing contract and stop
before implementation. Preserve a provider's failed prerequisite or refusal and stop
its dependent work; return it to the same owner. Do not search sibling plugin
installations, add a central registry, copy provider internals, self-review or
substitute raw tools to bypass a required provider. An advertised path that
fails needs its actual invocation error, not a guessed replacement path.

Pass these bindings and the approved bounded request to Adaptive Goal in this
main thread. This explicit recipe authorizes that composition without another
invocation. Continue a matching existing goal instead of creating another;
never replace an unrelated goal. When Ticket-to-PR or another explicit delivery
recipe calls implement, preserve the same goal, owner and delivery authority.
Adaptive Goal owns acceptance accounting, independent Review coordination,
repair history and completion. The delivery recipe retains its publication and
required-CI responsibilities. Do not start a separate execution owner.

## Implement at the agreed seams

Apply the selected principles guidance within the existing request. Follow the
selected Matt TDD workflow for behavior changes: write one failing test at the
approved public seam, observe the intended failure, implement that slice and
rerun the same command to green before another slice. For a purely mechanical
change, preserve the owner's applicable exact-oracle or passing-baseline evidence.

Write down the seams under test. Reuse confirmation already present in the
approved request, specification or inherited plan. Ask the human only for a
genuinely new or changed seam before writing its tests; do not reopen settled
seams as a ritual. Carry the unchanged confirmation into every assignment.

Run applicable typechecking and focused tests regularly, and the required full
suite on the final candidate. Use repository-defined commands and preserve
actual results; do not invent an unavailable check. Return literal red/green
commands and outcomes, changed files, candidate identity and any gaps.

After successful current checks, the existing owner invokes the bound independent
Review provider's complete public workflow. Review remains independent; its
success alone does not prove every acceptance criterion. Adaptive Goal maps
criteria to current evidence or gaps and owns any authorized repair and final
completion decision. A bounded implementor returns evidence instead of running
another acceptance or review cycle.

## Commit and preserve publication authority

Standalone implement defaults to one local commit on the current branch using
native Git and repository instructions, after required current checks, acceptance
evidence and independent Review clear. Honor an inherited no-commit instruction or narrower
assignment. Intermediate commits require the enclosing owner's explicit allowance
and focused checks; they do not establish final acceptance.

Push and PR creation each require explicit authority in the invocation or an
inherited delivery envelope. Bind those public operations only when authorized,
and preserve their verification requirements. A local implementation request
supplies neither effect. Never infer tracker mutation, merge, release or deployment
from completion. Provider refusal stops the dependent effect without bypass.

Return the actual candidate and local commit, changed files, check outcomes,
review evidence or gaps, acceptance coverage and separately authorized publication
results to the same owner. State any concrete blocker and next needed action;
never claim completion from package presence, a plan, or review alone.
