# Isolated ticket workers

Use this optional placement within the existing main-thread goal when fresh
ticket context repays handoff, rereading and integration overhead. Record that
basis, including for a same-route sequential assignment. Size or ticket count
alone does not justify it. Ordinary direct placement remains available.

## Bind scope and effects

Before affected mutation, bind the authoritative specification, explicit finite
ticket set, dependencies, criteria, shared decisions, preserved local work and
permitted effects. Read/list capabilities do not imply complete ticket discovery.
Missing material decisions, evidence or prerequisites stop affected work.

This strategy requires independent verification of the complete specification
at the end, with independent review as a required assessment, including routine
risk. Bind the compatible public capabilities during read-only preflight,
before goal activation or worker effects. Missing assurance stops launch;
self-review and routine-placement defaults do not satisfy this prerequisite.

Worker branches, linked worktrees, local commits and integration need explicit
user or preserved caller authority. Strategy selection grants none and does not
relocate the delivery checkout. Follow the already-bound public Git capabilities
for new branch and worktree creation and commits. Their refusals still stop the
operation; raw Git is not a workaround.

During read-only preflight, bind fresh worker allocation separately from
delivery-branch discovery, reuse or exact preparation. Each worker needs the
advertised **new-branch and linked-worktree creation** capability (Darrow Git's
`create-branch`), which owns naming from the ticket work. Do not turn that
creation intent into `prepare-task-branch` merely by constructing a name first.
A correlated existing delivery branch remains the integration branch and cannot
satisfy a fresh worker request. Invoke creation from the integration checkout
after checking its branch and pinned current `HEAD`; use the capability's
current-HEAD default. Pass `--from` only when its public contract permits the
user-named base. This prebinding rule does not bypass an actual refusal.

Prebind the matching public **commit** skill too. Every worker assignment must
carry its exact advertised name and instruction reference and require the worker
to invoke it for each local implementation or repair commit. A fresh worker
cannot inherit the parent's skill reads. Do not say the capability is optional
or allow plain `git commit` instead. Reconcile repository rules and the bound
provider's message constraints before assigning work; do not introduce forbidden
attribution or waive a provider refusal. Intermediate commits are exempt only
from the final-candidate assurance dependency, never from capability bindings,
message invariants or refusals.

## Plan bounded batches

Parallelize only independent substantial tickets with disjoint owned files,
settled interfaces, runnable focused checks and available host capacity. Keep
coupled or overlapping tickets sequential. Fresh context alone may justify a
sequential worker; it does not justify concurrency.

Pin one known integration branch and commit for the whole parallel batch. All
its workers, branches and linked worktrees start from that same commit; recheck
the integration tip before each allocation. A changed tip stops affected work
until the intended common base is clear. Wait for **every assignment in the
batch to settle before any integration or next-batch dispatch**. Do not roll a
new assignment in when one worker finishes. Land the settled batch serially,
then dispatch dependents from the updated integration branch only after their
prerequisite commits have landed. Worker completion or tracker closure alone
does not unblock a dependency.

## Assign one ticket

Keep the native goal, conversation, decisions, integration, verification
scheduling, repair accounting, completion and publication in this main thread.
Create a distinct worker branch and linked worktree from the known current
integration commit. Give the fresh worker a self-contained assignment with that
commit and absolute path, specification, criteria, interfaces, owned files,
allowed effects, preserved work, exact public capability references and checks.
Preserve required readiness, public seams and failing-before/passing-after
evidence. Keep the host-returned worker identity for repairs.

The worker owns only this assignment. It must not invoke Adaptive Goal, create
child goals, expand scope, coordinate independent assessments, publish a PR or
change tracker state. It returns the ordered full commit IDs, changed files,
actual checks and unresolved gaps or blockers. These local implementation
commits are intermediate results, not verified delivery or publication.

## Integrate the returned commits

Receive worker results through native host wait and follow-up controls. Inspect
the returned result: a blocker, refusal or unavailable required check stops
affected work and remains an evidence gap, including during repair. Do not
shell-poll for a commit from a settled worker or repeat denied actions. Preserve
the refusal and report what prerequisite must change before resuming.

Settle implementation before landing. On the one integration branch,
**cherry-pick the returned commits serially**; do not fast-forward or merge the
worker branch. Immediately before each landing, recheck the integration branch
and current tip against the expected tip, and inspect the exact intended commit,
its ancestry and changed files against the assignment. Confirm the landed tip
before the next commit. Preserve user edits and unrelated worktrees.

A changed tip, missing prerequisite or conflict stops landing. Return the
concrete state to the relevant retained worker; do not reset user work, force
refs or silently resolve out-of-scope edits. Resume only after the intended
candidate and authorized resolution are clear. Dependents start from the
updated integration branch after their prerequisites have landed, not from a
tracker closure or a worker's completion claim.

Run all required combined checks successfully after integration. Required
independent verification then assesses the complete specification at the end,
through the bound capability. Do not run separate ticket assessment cycles.
Missing fixtures, services or skipped required checks remain evidence gaps.

Return findings to the retained producing worker with current integration
state, then integrate repairs and refresh invalidated combined checks before
the existing follow-up assessment. Section 7 and the verification lifecycle own
repair routing and the one shared allowance. Feedback and cancellation remain
with the original main thread. Authorized publication still produces one
combined PR, with the existing verified-candidate and publication gates.
